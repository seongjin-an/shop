### 3. Dead Letter Topic (DLT) 패턴 도입

**목적**: 15번 재시도(5×@Retryable + 3×DefaultErrorHandler) 소진 후에도 메시지 보존

**수정/생성 파일**:
- `shop-stock/.../config/KafkaConfig.java`
  - `DefaultErrorHandler` recovery를 `DeadLetterPublishingRecoverer`로 교체
  - 실패 메시지 → `{원본토픽}-DLT` 파티션 0으로 라우팅
  - `dltKafkaListenerContainerFactory` 빈 추가 (AckMode.RECORD, ErrorHandler 없음)
- `shop-stock/.../kafka/StockDltConsumer.java` (신규)
  - `payment-success-DLT`, `order-canceled-DLT` 구독
  - `DltRetryService`에 재처리 위임
- `shop-stock/.../usecase/DltRetryService.java` (신규)
  - `@Retryable(maxAttempts=10, delay=3000, multiplier=1.5, maxDelay=30000)`
  - 스트레스 테스트 종료 후 경합이 가라앉을 때까지 대기하는 전략
- `shop-stock/src/main/resources/application.yml`
  - `payment-success-dlt`, `order-cancelled-dlt` 토픽 프로퍼티 추가
- `docker/create-topics.sh`
  - `payment-success-DLT`, `order-canceled-DLT` 토픽 생성 (파티션 1개 고정)

**재시도 레이어 4단계**:
```
[1] @Retryable × 5          50ms~500ms 간격
[2] DefaultErrorHandler × 3  2초 간격
         → DLT 토픽으로 라우팅
[3] DltRetryService × 10    3초~30초 간격 (경합 가라앉을 때까지 대기)
[4] 로그 + 수동 개입
```

## 핵심 설계 결정 및 근거

### 낙관적 락 vs 비관적 락
- 현재: 낙관적 락 유지 (학습 목적, 구조 잘 잡혀있음)
- 실무 고트래픽: Redis 재고 차감 + 비관적 락(금융) 혼용
- shop-stock 스케일 아웃은 Redis 재고 차감 없이는 역효과

### DLT 설계 원칙
- DLT → 또 다른 DLT 무한루프 방지: `dltKafkaListenerContainerFactory`에 ErrorHandler 없음
- DLT 컨슈머 실패 시 로그만 남기고 종료 (수동 개입)
- DLT는 메시지 보존, DltRetryService의 긴 backoff가 경합 회피

### shop-stock 스케일 아웃 한계
```
인스턴스 3개 × concurrency 3 = 최대 9 스레드가 동시에 같은 StockEntity 접근
→ 낙관적 락 충돌 9배 → @Retryable 소진 → DLT 폭발
→ Redis 재고 차감 도입 후에야 수평 확장 의미 있음
```
