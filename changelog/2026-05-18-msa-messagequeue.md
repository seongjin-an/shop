# 모놀리식 → MSA 전환, 메시지 큐의 역할

## 1. 왜 모놀리식에서 MSA로 전환했는가

### 모놀리식의 시작은 합리적이다

초기 스타트업은 팀이 작고 기능을 빠르게 추가해야 하기 때문에, 하나의 코드베이스와 하나의 배포 단위로 구성된 모놀리식이 최선의 선택이다. 문제는 **서비스가 성공해서 규모가 커졌을 때** 발생한다.

### 모놀리식의 한계

- **배포 문제**
  - 결제팀이 버그를 수정해도 전체 서비스를 재배포해야 한다. 상품팀, 주문팀 코드는 변경이 없어도 함께 배포된다. 이로 인해 배포 주기가 길어지고, 결국 배포 자체가 두려운 이벤트가 된다.

- **확장 문제**
  - 블랙프라이데이에 주문 트래픽이 10배 급증하면, 실제로는 주문 모듈만 확장하면 되지만 전체 서버를 함께 늘려야 한다. 결제, 상품, 회원 서버까지 같이 확장되어 비용이 낭비된다.

- **기술 부채 문제**
  - 레거시 Java 8 코드베이스에서 새로운 기능에 최신 기술을 적용하려면 전체 코드베이스를 한 번에 마이그레이션해야 한다. 이는 수년이 걸리는 작업이 된다.

- **팀 규모 문제**
  - 개발자 200명이 하나의 코드베이스에서 작업하면 머지 컨플릭트가 빈번하게 발생하고, 코드 오너십이 불분명해진다.

> Conway의 법칙: "시스템 구조는 조직 구조를 따라간다"  
> 팀이 커지면 아키텍처도 자연스럽게 분리된다.

## 2. MSA의 장단점

### 장점

| 항목 | 내용 |
|------|------|
| **독립 배포** | 결제 서비스만 배포해도 다른 서비스에 영향 없음 |
| **독립 확장** | 주문 서비스만 선택적으로 확장 가능 |
| **기술 독립성** | 서비스마다 다른 언어, 다른 DB 선택 가능 |
| **장애 격리** | 결제 서비스가 죽어도 상품 조회는 동작 |
| **팀 자율성** | 각 팀이 자기 서비스를 완전히 소유 |

### 단점

MSA는 복잡도를 없애는 것이 아니라, **분산 시스템의 복잡도를 내 문제로 가져오는 것**이다.

**모놀리식에서의 트랜잭션**
```
주문 생성 → 재고 감소 → 결제
→ 하나의 DB 트랜잭션으로 처리
→ 실패하면 전체 롤백
```

**MSA에서의 트랜잭션**
```
주문 서비스 → (네트워크) → 재고 서비스 → (네트워크) → 결제 서비스
→ 중간에 네트워크 실패?
→ 재고는 감소했는데 결제가 실패?
→ Saga, Outbox, Inbox 패턴이 필요한 이유
```

| 항목 | 내용 |
|------|------|
| **분산 트랜잭션** | ACID 보장 불가 → Saga 패턴 필요 |
| **네트워크 신뢰성** | 서비스 간 통신 실패를 항상 고려해야 함 |
| **운영 복잡도** | 서비스 10개 → 로그, 모니터링 10배 |
| **테스트 어려움** | 통합 테스트 환경 구성이 복잡 |
| **지연 시간** | 함수 호출이 네트워크 호출로 바뀜 |

## 3. 서비스 간 통신과 메시지 큐의 등장

MSA에서 서비스 간 통신 방법은 두 가지다.

### 동기 통신 (REST / gRPC)

```
Order ──HTTP──→ Stock ──HTTP──→ Payment
```

- Stock이 응답이 느리면 Order가 기다려야 한다
- Payment가 죽으면 Order도 실패한다
- 서비스들이 **강하게 결합**된다

### 비동기 통신 (메시지 큐)

```
Order → [Queue] → Stock
Order → [Queue] → Payment
```

- Order는 메시지를 넣고 바로 응답을 반환한다
- Stock, Payment는 준비됐을 때 꺼내서 처리한다
- 서비스들이 **느슨하게 결합**된다

## 4. 메시지 큐의 핵심 특징

### 비동기 / 디커플링

발행자(Publisher)는 소비자(Consumer)가 살아있는지 모른다. 소비자가 죽어 있어도 메시지는 큐에 보관된다. 서비스 장애가 전파되지 않는다.

### 버퍼링 (부하 흡수)

```
초당 10,000 주문 → Queue → Stock 서비스 (초당 1,000 처리 가능)

Queue 없음: Stock 서버 과부하 → 전체 장애
Queue 있음: 밀린 메시지가 Queue에 쌓임 → 느리지만 처리됨
```

### 재처리 가능

결제 서비스가 일시적으로 죽었다가 살아나도, 큐에 쌓인 메시지를 다시 처리할 수 있다. 데이터 유실이 없다.

### 팬아웃 (Fan-out)

```
payment-success 이벤트 하나 발행
  → Order 서비스  (주문 완료 처리)
  → Stock 서비스  (재고 확정)
  → 알림 서비스   (SMS 발송)
  → 포인트 서비스 (적립)
```

발행자는 수신자가 몇 개인지 모르고, 알 필요도 없다.

## 5. 메시지 큐의 장단점

### 장점

| 항목 | 내용 |
|------|------|
| **내결함성** | 소비자 장애 시 메시지 유실 없음 |
| **확장성** | 소비자 인스턴스를 늘리면 처리량 선형 증가 |
| **디커플링** | 발행자/소비자 독립적 배포 가능 |
| **순서 보장** | 파티션 내에서 순서 보장 (Kafka 기준) |

### 단점

| 항목 | 내용 |
|------|------|
| **최종 일관성** | 즉시 반영이 아님, 지연 존재 |
| **중복 처리** | At-least-once 보장 → Inbox 패턴 필요 |
| **순서 문제** | 파티션을 넘어가면 순서 보장 안 됨 |
| **디버깅 어려움** | 비동기라 흐름 추적이 어려움 |
| **인프라 부담** | Kafka 자체를 운영해야 함 |

## 6. 전체 흐름 정리

```
모놀리식
  장점: 단순함, 트랜잭션 보장
  단점: 규모가 커지면 배포/확장/팀 문제
         ↓ 성장
MSA 전환
  해결: 독립 배포, 독립 확장, 팀 자율성
  새 문제: 분산 트랜잭션, 네트워크 실패, 부분 장애
         ↓ 해결책
메시지 큐 도입
  해결: 서비스 간 느슨한 결합, 장애 격리, 버퍼링
  새 문제: 최종 일관성, 중복 처리, 순서 문제
         ↓ 해결책
Saga + Outbox + Inbox 패턴
  → 이 프로젝트(shop)가 구현하고 있는 내용
```

## 7. 핵심 요약

> MSA를 선택하는 것은 복잡도를 없애는 것이 아니라, **"복잡도를 어디에 둘 것인가"를 선택하는 것**이다.
>
> - 모놀리식의 복잡도는 **코드베이스 안**에 있다
> - MSA의 복잡도는 **서비스 간 통신과 데이터 일관성**에 있다
>
> 메시지 큐는 MSA의 핵심 복잡도인 "서비스 간 강한 결합"을 해소하기 위한 도구다. 단, 메시지 큐를 도입하면 최종 일관성, 중복 처리, 순서 보장이라는 새로운 복잡도가 생기고, 이를 해결하기 위해 Saga, Outbox, Inbox 패턴이 필요해진다.
