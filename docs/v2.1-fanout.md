## 2. fan-out 이 뭔지 먼저

**Fan-out = "한 개의 입력 이벤트를 N 개로 쪼개서 흘려보내는 것"**.

상식적인 비유: 택배센터에서 "서울행 트럭 한 대"로 보내던 짐을, **"상품별로 쪼개서 각기 다른 분류벨트에 태우는 것"** 이 fan-out. 각 벨트가 독립적으로 빠르게 움직입니다.

반대 개념이 **fan-in (aggregator)**: 쪼개진 것들의 결과를 다시 모으는 쪽. 배송 완료 보고를 "주문 단위"로 다시 합쳐야 하니까요.

이 프로젝트에서는:

**Before (order-level)** — 이벤트가 주문 단위로 하나:
```
shop-order  ──[order-created: {items: [A, B, C]}]──▶  shop-stock
                                                        한 트랜잭션에 A, B, C 다 처리
```

**After (per-item fan-out)** — 이벤트가 상품 단위로 N 개:
```
shop-order ──[stock-reservation-requested, key=A, {productId:A, qty:2, sagaId:S1, itemCount:3}]──▶
            ──[stock-reservation-requested, key=B, {productId:B, qty:1, sagaId:S1, itemCount:3}]──▶
            ──[stock-reservation-requested, key=C, {productId:C, qty:3, sagaId:S1, itemCount:3}]──▶
            
            shop-stock: partition key = productId 이므로
                A, B, C 가 서로 다른 파티션으로 흩어짐 → 병렬 처리
```

## 3. 전체 흐름 단계별 (fan-out 반영)

### [1단계] 주문 접수

```
[Client] POST /orders  {items: [A×2, B×1, C×3]}
   ↓
shop-order (8082):
   ├─ sagaId = S1 생성
   ├─ OrderEntity(status=PENDING) INSERT
   ├─ OrderItemEntity 3건 INSERT  (양방향 관계 addItem)
   │
   └─ ★ FAN-OUT ★
       Kafka 로 3 개 이벤트 발행 (각각 key=productId)
       ├─ stock-reservation-requested, key=A
       ├─ stock-reservation-requested, key=B
       └─ stock-reservation-requested, key=C
```

### [2단계] 재고 예약 — 3 스레드가 병렬로

```
shop-stock (8083):
   3 개 파티션 × 3 concurrency = 3 스레드 동시 소비

   Thread-1 (partition 0, productId=A): 
     ├─ Inbox dedup (eventId)
     ├─ StockEntity(A).reserve(2)  → quantity--, reservedQuantity++
     └─ stock-reserved 발행 (key=A, sagaId=S1)

   Thread-2 (partition 1, productId=B): 동일
   Thread-3 (partition 2, productId=C): 재고 부족!
     └─ stock-reserve-failed 발행 (key=C, sagaId=S1)
```

*(만약 C 가 재고 충분했다면 모두 stock-reserved 발행)*

### [3단계] FAN-IN (aggregator) — shop-order 가 결과를 모음

```
shop-order:
   stock-reserved / stock-reserve-failed 를 sagaId=S1 로 집계
   
   3 건 모두 모일 때까지 대기 (Order 엔티티에 "몇 건 도착했는지" 카운트)
   
   [케이스 α] 3 건 모두 stock-reserved
     ├─ order.stockReserved() → STOCK_RESERVED
     └─ payment-requested 발행 (key=sagaId, 1건)
   
   [케이스 β] 1건이라도 stock-reserve-failed
     ├─ order.stockFailed() → STOCK_FAILED (terminal)
     └─ ★ 이미 성공한 A, B 는 보상 필요! ★
         ├─ stock-release-requested, key=A ─┐
         └─ stock-release-requested, key=B ─┘ (C 는 reserve 실패라 skip)
```

**여기가 fan-in 의 핵심** — "부분 실패" 를 판단하고, 성공한 아이템만 골라서 보상 fan-out 을 다시 날리는 역할.

### [4단계] 결제 (정상 흐름 가정)

```
shop-payment (8084):  web-application-type: none, Kafka 전용
   payment-requested 수신
     ├─ Inbox dedup
     ├─ Fake PG 호출 (90% 성공)
     ├─ PaymentEntity 저장 (pgProvider=FAKE_PG, method=CARD)
     │
     ├─ 성공(90%): payment-success 발행
     └─ 실패(10%): payment-failed 발행
```

### [5단계-α] 결제 성공 → 재고 확정 fan-out

```
shop-order:
   payment-success 수신
     ├─ order.paymentCompleted() → COMPLETED (terminal)
     │
     └─ ★ FAN-OUT (확정) ★
         OrderItem 3 개마다:
         ├─ stock-confirm-requested, key=A
         ├─ stock-confirm-requested, key=B
         └─ stock-confirm-requested, key=C

shop-stock:
   3 스레드 병렬로 confirmReservation
     reservedQuantity-- (판매 확정, quantity 는 이미 차감돼 있음)
```

### [5단계-β] 결제 실패 → 재고 해제 fan-out

```
shop-order:
   payment-failed 수신
     ├─ order.paymentFailed() → PAYMENT_FAILED
     │
     └─ ★ FAN-OUT (해제/보상) ★
         OrderItem 3 개마다:
         ├─ stock-release-requested, key=A
         ├─ stock-release-requested, key=B
         └─ stock-release-requested, key=C

shop-stock:
   3 스레드 병렬로 cancelReservation
     reservedQuantity--, quantity++ (원상복귀)

shop-order:
   (모든 release 처리 완료 가정)
     └─ order.compensationCompleted() → CANCELLED (terminal)
```

## 4. 각 서비스의 역할 한 줄 요약

| 서비스 | fan-out 하는 주체? | fan-in 하는 주체? | 하는 일 |
|--------|-------------------|------------------|---------|
| shop-order | ✅ (reservation/confirm/release) | ✅ (stock-reserved/failed 집계) | Saga 조율, 상태머신 |
| shop-stock | ❌ | ❌ | 단일 아이템 단위 DB 작업만 |
| shop-payment | ❌ | ❌ | 결제 한 건 처리 |
| shop-product | ❌ | ❌ | 상품 CRUD, product-created 발행 |

**shop-order 가 유일한 조율자**. fan-out 과 aggregator 둘 다 shop-order 안에 있습니다. shop-stock 은 "벙어리 worker" 처럼 자기 아이템만 처리합니다.

## 5. 왜 fan-out 을 도입했나 (원래 배경)

**이전 구조 (order-level)**:
```
order-created {items:[A,B,C]}
   ↓
shop-stock: 한 트랜잭션
   ├─ UPDATE stock WHERE productId=A
   ├─ UPDATE stock WHERE productId=B
   └─ UPDATE stock WHERE productId=C
   COMMIT
```

문제들:
1. **트랜잭션이 김** — 3개 row 모두 락 잡고 커밋까지. 동시 주문이 쌓이면 데드락/대기.
2. **한 상품이 핫하면 전체 느려짐** — B 가 인기 상품이면 여러 주문이 B 의 row 를 두고 경합 → 전체 주문이 느림
3. **낙관락 충돌 잦음** — 다른 주문이 B 를 동시에 건드릴 때마다 OLE → 재시도
4. **단일 실패가 전체 롤백** — C 재고 부족이면 A, B 의 reserve 도 트랜잭션 롤백 (이건 장점이긴 함)

**fan-out 의 노림수**:
- productId 를 **파티션 key** 로 쓰면, 같은 상품 A 의 모든 예약/확정/해제가 **같은 파티션 → 같은 스레드** 로 흘러감 → **single-writer-per-aggregate** 달성.
- 동시성 없이 직렬 처리 → **낙관락 불필요** (이론상).
- 상품별로 병렬이라 **처리량 ↑**.

## 6. 그런데 왜 문제가 터졌나 (이전 대화와 연결)

위 "single-writer" 전제의 구멍을 다시 강조하면:

**Partition key 는 _단일 토픽 안에서만_ 순서를 보장**합니다. 그런데 shop-stock 은 **세 토픽** 을 구독합니다:

```
stock-reservation-requested   ──▶ Thread-A  (reserve)
stock-confirm-requested       ──▶ Thread-B  (confirm)
stock-release-requested       ──▶ Thread-C  (release)
```

세 토픽 각각이 독립적인 컨슈머 스레드풀입니다. 같은 productId=A 에 대해:

```
시각 t=0:  사가 S1 의 reserve(A) 가 Thread-A 에서 처리 중 (version=5 읽음)
시각 t=1:  사가 S0 의 release(A) 가 Thread-C 에서 처리 중 (version=5 읽음)
시각 t=2:  Thread-A 가 먼저 flush → version=5→6, OK
시각 t=3:  Thread-C 가 flush 시도 → version=5 기대, 실제=6 → OLE!
```

**"single-writer" 가 토픽 경계를 넘지 못한 것.** 그래서 낙관락 예외가 집요하게 나고, DLT 로 밀려나고, reservedQuantity 가 영영 안 돌아와서 26 까지 드리프트된 겁니다.

## 7. 전체를 한 장의 그림으로

```
                       ┌──────────────────┐
                       │   shop-frontend  │
                       └────────┬─────────┘
                                │ POST /orders
                                ▼
  ┌──────────────────────────────────────────────────────┐
  │                    shop-order                         │
  │                                                       │
  │  OrderEntity(PENDING)                                │
  │       │                                              │
  │       ├─ FAN-OUT → stock-reservation-requested ×N    │
  │       │                                              │
  │       ◀─ FAN-IN ← stock-reserved / stock-reserve-failed ×N
  │       │                                              │
  │       ├─ 전원 성공 → payment-requested               │
  │       │                                              │
  │       ◀─ payment-success / payment-failed            │
  │       │                                              │
  │       ├─ 성공 → FAN-OUT stock-confirm-requested ×N   │
  │       └─ 실패 → FAN-OUT stock-release-requested ×N   │
  └───────┬──────────────────────────────┬───────────────┘
          │                              │
          ▼                              ▼
  ┌───────────────┐              ┌──────────────┐
  │  shop-stock   │              │ shop-payment │
  │               │              │   (Fake PG)  │
  │ Thread-A (A)  │              └──────────────┘
  │ Thread-B (B)  │  ◀─ 세 개의 서로 다른 컨슈머 그룹
  │ Thread-C (C)  │     (reservation / confirm / release)
  │               │     가 같은 row 를 경합할 수 있다 ← 버그 원인
  └───────────────┘
```

---

정리: **fan-out = 주문 단위 이벤트를 상품 단위로 쪼개는 것**, **fan-in = 결과를 다시 주문 단위로 모으는 것**. 쪼개는 주체도 모으는 주체도 shop-order. shop-stock 은 상품 하나씩 묵묵히 처리하는 일꾼. 이 구조의 장점(병렬성)과 함정(토픽 경계를 넘는 경합)을 그대로 안고 있고, 함정이 바로 이전에 진단한 OLE → DLT → reserved_quantity 드리프트입니다.
